## [HIGH] Finding 3 — Concurrent dict mutation in _mtf_cache from parallel threads
File: /home/mrc/opentrader/harness.py, lines 1122–1123

What goes wrong:
  In `_debate_one_symbol()`, the multi-timeframe cache is written to from
  multiple `ThreadPoolExecutor` threads (spawned at line 1300-1305). The
  assignment `self._mtf_cache[mtf_cache_key] = {"bars": bars, "ts": time.time()}`
  can trigger a CPython dict resize (hash table reallocation) while another
  thread is reading from the same dict at line 1115. Under the GIL, dict writes
  are not fully atomic during resize — concurrent readers can observe
  corrupted/inconsistent iteration state.

Quoted evidence:
  Line 1115:   mtf_entry = self._mtf_cache.get(mtf_cache_key, {})  # reader
  Line 1123:   self._mtf_cache[mtf_cache_key] = {"bars": bars, "ts": time.time()}  # writer

Suggested fix:
  Wrap all reads and writes to `self._mtf_cache` in a `threading.Lock`:
    with self._mtf_lock:
        mtf_entry = self._mtf_cache.get(mtf_cache_key, {})
  (Add `self._mtf_lock = threading.Lock()` to __init__.)

## [HIGH] Finding 4 — Data race on shared cache in parallel debate threads
File: /home/mrc/opentrader/harness.py, lines 1089–1106

What goes wrong:
  Three instance-level caches (`_news_cache`, `_arxiv_cache`, `_econ_cache`)
  are guarded by `if sym == self.symbols[0]` to ensure only one fetch per cycle.
  However, in the parallel path (ThreadPoolExecutor at line 1300), ALL threads
  check this guard simultaneously. Multiple threads can pass the check before
  any of them writes. This causes redundant external API calls (fetch_all_news,
  fetch_arxiv, get_economics) and a race on which thread's write persists.

Quoted evidence:
  Line 1089-1090:  if sym == self.symbols[0]:  # fetch once per cycle
                       self._econ_cache = json.dumps(self.mcp.get_economics())
  Line 1099-1101:  if sym == self.symbols[0]:
                       self._news_cache = fetch_all_news()
                       self._arxiv_cache = fetch_arxiv()

Suggested fix:
  Use a cycle-based flag instead of a symbol comparison:
    if self._news_cache_cycle != self.cycle:
        self._news_cache_cycle = self.cycle
        self._news_cache = fetch_all_news()
  Or use a threading.Lock to protect the fetch-once-per-cycle logic.

## [HIGH] Finding 5 — AgentScorer in-memory state race between record() and _save()
File: /home/mrc/opentrader/mot/scoring.py, lines 68–113

What goes wrong:
  The `_lock` in AgentScorer only guards the file write (lines 76-79), not the
  in-memory `self.records` dict. `_save()` prepares data by iterating
  `self.records.items()` outside the lock (line 69-75), while `record()` mutates
  the same dict (lines 88-102) from parallel debate threads. A thread context
  switch during dict iteration while another thread mutates the dict can cause
  `RuntimeError: dictionary changed size during iteration`.

Quoted evidence:
  Line 56-57:   self.records: Dict[str, AgentRecord] = self._load()
                self._lock = threading.Lock()
  Line 68-75:   # _save() reads self.records OUTSIDE the lock:
                data = {k: {...} for k, v in self.records.items()}  # NO LOCK
  Line 76:      with self._lock:  # lock only for file write
  Line 82-113:  # record() mutates self.records with NO lock:
  Line 89:      rec.total_decisions += 1
  Line 100:     rec.recent_scores.append(score)

Suggested fix:
  Move the lock acquisition to cover both the dict read (data preparation in
  _save) and the dict mutations in record():
    def record(...):
        with self._lock:
            ...  # all mutations
            self._save_locked()  # write without re-acquiring

## [HIGH] Finding 6 — State save failure logged at DEBUG level (invisible data loss)
File: /home/mrc/opentrader/harness.py, lines 467–469

What goes wrong:
  `_save_agent_state()` catches all exceptions and logs at DEBUG level. At the
  default INFO log level, a failure to persist agent state (positions, cash,
  trade journal, signal history) produces NO visible output. If the disk is
  full or the JSON serializer fails on a non-serializable object, the state is
  silently lost with no alert. Since `_save_agent_state()` is called every cycle
  (line 1706), a transient issue can go completely unnoticed.

Quoted evidence:
  Line 465-469:
      path = self._agent_state_path()
      with open(path, "w") as f:
          json.dump(state, f, indent=2, default=str)
  except Exception as e:
      logger.debug(f"Could not save agent state: {e}")

Suggested fix:
  Change to `logger.error()` (or at minimum `logger.warning()`) to surface
  state persistence failures in production logs. Also consider writing to a
  temporary file and atomically renaming (as StateManager does at line 68-71),
  so a partial write doesn't corrupt the previous state on disk.

## [HIGH] Finding 7 — Cost basis reconstructed incorrectly on portfolio restore
File: /home/mrc/opentrader/harness.py, lines 528–535

What goes wrong:
  When restoring portfolio state from `paper_state.json`, the cost basis is
  computed as `qty * entry_price` using a single entry price per position.
  However, the live exchange accumulates cost basis as a running sum of all
  buy fill costs (`self._cost_basis[sym] = self._cost_basis.get(sym, 0) + cost`
  at live.py line 250). If a position was accumulated via multiple buys at
  different prices, the restored cost basis will be wrong. The fills list IS
  saved but is NOT used to rebuild cost basis.

Quoted evidence:
  Line 528-535:
      restored_cost_basis = {}
      for p in saved_positions:
          ...
          restored_cost_basis[sym] = qty * entry  # assumes single-entry
  Compare with live.py line 250:
      self._cost_basis[symbol] = self._cost_basis.get(symbol, 0) + cost

Suggested fix:
  Reconstruct cost basis from the saved fills list rather than recomputing from
  positions. Sum all BUY fill costs per symbol:
      for f in saved_fills:
          if f["side"] == "BUY":
              restored_cost_basis[sym] = restored_cost_basis.get(sym, 0) + f["cost"]

## [MEDIUM] Finding 11 — Slippage applied symmetrically to filled quantity but cost uses effective_qty
File: /home/mrc/opentrader/exchange/paper.py, lines 85–101

What goes wrong:
  When cash is insufficient for a BUY, the quantity is reduced to `affordable_qty`
  (line 89). But the fill record at lines 125-129 still records the original
  `order_id`, and the `cost` is computed as `fill_price * effective_qty` (line 100).
  This is mathematically correct, BUT the cost recorded in the fill dict (line 128)
  uses the post-adjustment `effective_qty`, while `cash_after` uses `self._cash`
  which was decremented by `cost`. If multiple partial fills happen (slippage +
  cash cap + partial fill), the fill dict's `quantity` vs `cost` vs `cash_after`
  may not reconcile when audited later. This is a data integrity issue for
  post-hoc trade reconstruction.

Quoted evidence:
  Line 78-82:   effective_qty = quantity; ... if partial_fill: effective_qty *= fill_ratio
  Line 89:      affordable_qty = self._cash / fill_price
  Line 98:      effective_qty = affordable_qty
  Line 101:     self._cash -= cost
  Line 128:     "cost": round(cost, 2), "cash_after": round(self._cash, 2),

Suggested fix:
  Store the original requested quantity in the fill dict so the adjustment
  chain (requested → after-partial-fill → after-cash-cap → actual) is
  traceable. Add fields `requested_quantity` and `fill_pct` to the fill dict
  for auditability.

## [MEDIUM] Finding 13 — Harness main loop has no try/except around run_cycle()
File: /home/mrc/opentrader/harness.py, lines 1952–1957

What goes wrong:
  Any unhandled exception in `run_cycle()` propagates directly to the caller,
  killing the entire harness process. There is no retry, no graceful degrade,
  no state save before crash. Since `run_cycle()` performs ~2000 lines of
  orchestration (debate, risk, execution, state I/O, fine-tune subprocess),
  a single transient error (e.g., disk full, network timeout, JSON parse
  failure on LLM output) terminates the bot.

Quoted evidence:
  Line 1952-1957:
      while self.running:
          if self.max_cycles > 0 and self.cycle >= self.max_cycles:
              ...
          self.run_cycle()   # ← no try/except
          ...

Suggested fix:
  Wrap `self.run_cycle()` in a try/except that logs the error, saves state,
  and optionally continues after a backoff:
      try:
          self.run_cycle()
      except Exception as e:
          logger.error(f"Cycle {self.cycle} crashed: {e}", exc_info=True)
          self._save_agent_state()  # emergency persist
          time.sleep(5)

## [LOW] Finding 15 — LiveExchange get_bars cache key collision across limit values
File: /home/mrc/opentrader/exchange/live.py, lines 134–139

What goes wrong:
  The cache key format `f"{symbol}:{timeframe}:{limit}"` ties each specific
  limit value to its own cache entry. But when `load_bars()` is called at
  line 300-305, it writes to a different cache key format than `get_bars()`:
  `cache_key = f"{symbol}:1h:{len(bars)}"` — hardcoded "1h" regardless of
  the actual timeframe. If backtest data is loaded with 500 bars, then
  `get_bars()` requests 80 bars, there's no cache hit. More critically, the
  `_last_fetch` dict has independent TTL per cache key, so a stale entry
  with limit=100 doesn't prevent a fresh fetch with limit=80. This causes
  unnecessary API calls and cache fragmentation.

Quoted evidence:
  Line 134:   cache_key = f"{symbol}:{timeframe}:{limit}"    # get_bars cache key
  Line 302:   cache_key = f"{symbol}:1h:{len(bars)}"          # load_bars cache key (hardcoded 1h)
  Line 136-139:
      if cache_key in self._bar_cache:
          last_fetch = self._last_fetch.get(cache_key, 0)
          if now - last_fetch < self._cache_ttl:
              return self._bar_cache[cache_key]

Suggested fix:
  Pass the timeframe parameter to `load_bars()` so the cache key matches.
  Better: use a two-level cache (symbol + timeframe → list of bars),
  and slice bars[-limit:] on retrieval rather than keying by limit.
